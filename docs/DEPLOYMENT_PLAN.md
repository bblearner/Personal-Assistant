# Master Project Blueprint: Production Deployment & Code Specifications

This document serves as the comprehensive context file for automating production readiness and deployment setup. It bridges the system architecture with the security, hardening, and hosting requirements.

---

## 1. Production Infrastructure Architecture

The application transitions from a local Docker Compose setup to a fully managed, low-maintenance Platform-as-a-Service (PaaS) architecture:

- **Database (PostgreSQL):** Hosted on **Neon** or **Supabase**. This ensures durable, serverless operation with automated daily backups and point-in-time recovery.

- **Backend API (Golang):** Hosted on **Railway** or **Render**. It builds natively using the existing project configurations directly from the repository.

- **Frontend UI (Next.js):** Hosted on **Vercel**. This provides automatic branch previews, optimization, and edge-network content delivery.

### Git Workflow & Deployment Automation

A dual-branch strategy separates active iteration from live infrastructure:

- **`dev` Branch:** Used for local engineering, feature branches, and staging testing. Pushing here does not affect production.

- **`mainline` Branch:** Tracks the stable production state. Pushing or merging code into `mainline` triggers automated build pipelines on Vercel and Railway/Render for zero-downtime rolling updates.

## 2. Go Backend Required Code Changes

### A. Environment Fail-Fast Validation

Modify `main.go` to validate infrastructure requirements during the boot phase. If any required variable is missing or malformed, invoke `log.Fatalf()` to crash the container immediately during deployment, preventing a broken app from going live:

- `DATABASE_URL`: Connection string for the managed Postgres instance.

- `API_SECRET_KEY`: Random 32-byte hexadecimal string for single-user authorization.

- `FRONTEND_URL`: The production URL generated by Vercel.

### B. Hardened HTTP Server Timeouts

Replace default server initializations with explicit network constraints to prevent resource exhaustion from hanging or stalled sockets:

- `ReadTimeout`: 5 seconds

- `WriteTimeout`: 10 seconds

- `IdleTimeout`: 120 seconds

### C. Structured Logging Middleware

Implement a global interceptor using Go's native `slog` library. Every HTTP interaction must print a structured JSON payload to standard output (`stdout`), mapping:

- `method`: HTTP Request Verb

- `path`: Requested URI path

- `duration`: Compute string delta of elapsed processing time

- `ip`: Connecting remote address

- `response`: Response sent back to the client

### D. Strict Cross-Origin Resource Sharing (CORS)

Do not allow wildcard (`*`) origins. Create or utilize a standard middleware that reads the `FRONTEND_URL` environment variable and binds it directly to the HTTP `Access-Control-Allow-Origin` headers.

### E. Single-User Token Authentication Middleware

Enforce a perimeter barrier across all application API paths. Create a middleware that inspects the incoming `Authorization` header.

- Expect string structure: `Bearer <API_SECRET_KEY>`.

- If the token is missing, malformed, or mismatching, drop the request instantly and issue a `401 Unauthorized` response code.

## 3. Next.js Frontend Required Code Changes

### A. Environment Variables Setup

Configure the frontend repository to securely bind production endpoints. The client-side application requires accessibility to:

- `NEXT_PUBLIC_API_URL`: The live hosting service domain generated by Railway/Render.

- `NEXT_PUBLIC_API_KEY`: The matching authentication token string required by the backend.

### B. Network Client Interception Layer

Modify the root data fetching modules (native `fetch`, Axios instance, or TanStack Query custom clients).

- Intercept every outbound network call routing to `NEXT_PUBLIC_API_URL`.

- Automatically attach the authorization string to the headers of every request:

```http
Authorization: Bearer <NEXT_PUBLIC_API_KEY>

```

## 4. Execution Step Summary (Order of Operations)

1. **Database Provisioning:** Spin up the target managed Postgres cluster and run the core relational/JSONB table schemas.

2. **Backend Modernization:** Inject the validation checks, timeouts, and logging/auth middlewares into the Go repository.

3. **Frontend Update:** Inject environment variables and update network clients to append headers.

4. **Deployment Linking:** Connect GitHub webhooks to Vercel and Railway/Render, feeding the validated secrets across their respective dashboards.

5. **Production Verification:** Execute a manual merge of tested `dev` structures into `mainline` to execute live builds.
